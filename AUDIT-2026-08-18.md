# A11y Charts restart-readiness audit

**Audit date:** August 18, 2026
**Environment:** local working tree at `8c75e34` on `main`, plus three pre-existing uncommitted files
**Application:** Angular demo at `http://127.0.0.1:4200/`
**Compliance profile:** the required target was not supplied. Accessibility findings are mapped provisionally to **WCAG 2.2 Level AA**; Section 508, EN 301 549, and AAA were not graded.

## Executive verdict

The project has a promising and unusually thoughtful accessible-chart foundation, but it is **not restart-ready as a passing baseline** yet.

The production build fails, all three existing unit tests fail before their assertions, Angular 18 is unsupported and the production dependency tree contains 9 known vulnerabilities, and a reusable component does not react when its `data` input changes after first render. Under the provisional WCAG 2.2 AA benchmark, the current page also has confirmed failures involving multi-instance descriptions, mobile reflow, the custom keyboard surface's role, and target-series contrast. A WCAG conformance claim should not be made from this build.

The highest-value first milestone is a short stabilization sprint: protect the current experiment, choose whether this is a library or demo application, upgrade the framework/chart stack, restore green build and test gates, fix input reactivity, then correct the four shared accessibility defects. Most defects are concentrated in one component and should be economical to retest.

## Scope and method

- Audited the one rendered route, `/`, containing two instances of the shared line-chart template.
- Audited default, keyboard-focused, first/last-year, series-disabled, pattern-selected, horizontal-overflow, and forced-high-contrast states.
- Tested exact viewport widths of 320, 375, 390, 480, 640, 768, 1024, 1280, and 1440 CSS px at 900 CSS px high.
- Used Chromium 151, axe-core 4.13.0, DOM/accessibility snapshots, native keyboard interaction, rendered bounding-box/overflow measurements, computed color analysis, and source review.
- Ran clean dependency installation, production build, headless unit tests, app/spec TypeScript checks, dependency audit/outdated checks, a development server, and `git diff --check`.
- No authenticated routes, network links, forms, downloads, server APIs, or destructive actions exist in the app.
- A desktop or mobile screen-reader smoke test was not available. Accessibility-tree and live-region inspection are not substitutes for VoiceOver, NVDA, JAWS, or TalkBack verification.
- Reduced-motion logic was reviewed in source but not browser-emulated. Forced-high-contrast rendering was visually inspected in headless Chromium.

## Target-compliance failures

### A11Y-01 - Reused IDs associate the second chart with the first chart

**Severity:** High
**Scope:** Every chart after the first; 1 of 2 current instances
**Target relationship:** Fails the provisional WCAG 2.2 AA benchmark

**Evidence**

- `a11y-line-chart.component.html:58-63` hard-codes `chartKeyboardHelp`, `chartScrollHelp`, and `perfChartData` for every component instance.
- The rendered document contained two copies of each ID.
- Both chart images exposed `aria-describedby="chartKeyboardHelp perfChartData"`.
- For instance 2, both ID references resolved outside its own `.perf-chart` and into instance 1. The two charts contain different years and values.

**User impact**

A screen-reader user entering the second chart can receive the first chart's keyboard help/data relationship instead of the second chart's data. The component's documented multi-instance promise is therefore not reliable.

**Standards**

[WCAG 2.2 SC 1.3.1, Info and Relationships](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html).

**Fix**

Generate stable per-instance IDs, use those values consistently in the template and `descIds`, and give the chart its specific title through `aria-labelledby`. Retest at least two instances and assert that every ID is unique and every IDREF resolves inside the same host component.

### A11Y-02 - The hidden data table breaks page reflow

**Severity:** High
**Scope:** Both chart instances at 320-480 CSS px
**Target relationship:** Fails the provisional WCAG 2.2 AA benchmark

**Evidence**

| Viewport | Document width | Overflow |
|---:|---:|---:|
| 320 | 573 | +253 px |
| 375 | 573 | +198 px |
| 390 | 573 | +183 px |
| 480 | 573 | +93 px |
| 640 | 640 | 0 px |

- The intended chart viewport correctly contained its 720 px-wide visual chart.
- The actual body overflow came from each `table.sr-only`, whose table layout remained about 550 px wide despite the generic 1 px visually-hidden rule.
- This is not the chart exception for intrinsically two-dimensional content; the unintended page overflow comes from content intended to be visually hidden.

**User impact**

At mobile widths and the equivalent 400% reflow condition, users can horizontally pan the whole page and lose stable reading alignment.

**Standards**

[WCAG 2.2 SC 1.4.10, Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

**Fix**

Use a table-safe visually-hidden technique (for example, visually hide a block wrapper around the table rather than forcing table layout itself to 1 px), then require `documentElement.scrollWidth === innerWidth` across the full viewport matrix. Keep intentional chart scrolling inside the named chart viewport.

### A11Y-03 - The keyboard surface has no valid interactive role

**Severity:** Medium
**Scope:** Both chart instances
**Target relationship:** Fails the provisional WCAG 2.2 AA benchmark

**Evidence**

- The focusable `.chart-focus-layer` is a plain `div` with an implicit generic role and keyboard behavior.
- It declares `aria-roledescription="interactive time series"`, but `aria-roledescription` is prohibited on that role.
- axe-core reported `aria-prohibited-attr` twice, once per chart.
- The accessibility snapshot exposed the control as `generic`, not as a component with a programmatically determinable interactive role/state.

**User impact**

Assistive technology receives instructions and changing text, but not a dependable role/state model for the control that consumes arrow, Home, and End keys.

**Standards**

[WCAG 2.2 SC 4.1.2, Name, Role, Value](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value).

**Fix**

Choose and document a valid interaction model, then expose the matching role and value/state semantics. A roving set of point controls or a carefully specified single value-selector control is easier to test than a generic full-canvas overlay. Remove `aria-roledescription` unless it is permitted for the selected role. Retest name, role, current value, key behavior, and live announcements with a real screen reader.

### A11Y-04 - Target-series contrast is below 3:1

**Severity:** Medium
**Scope:** Default target line, symbol, and legend in both charts
**Target relationship:** Fails the provisional WCAG 2.2 AA benchmark

**Evidence**

- The target color `#c1a100` measures **2.51:1** against white.
- It measures **1.82:1** against its `#e8dca4` target fill.
- The surrounding white outline does not repair the edge: target yellow against white is still 2.51:1.
- Forced-high-contrast Chromium retained the canvas's authored series colors. The new pattern selects are optional and default to `None`.

**User impact**

Low-vision users can struggle to distinguish the target line and diamonds from the fill/background, especially where the series overlap.

**Standards**

[WCAG 2.2 SC 1.4.11, Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

**Fix**

Darken the default target stroke/symbol or add a persistent contrasting edge/pattern that reaches 3:1 against every adjacent color. Measure default, hover/emphasis, overlap, legend, and forced-color states; do not require users to discover a pattern preference to obtain the compliant default.

## Functional and restart-readiness findings

### FUNC-01 - Production build and test gates are red

**Severity:** High
**Scope:** Repository-wide
**Target relationship:** Not standards-based

**Evidence**

- Production build fails because `a11y-line-chart.component.scss` compiles to 5.08 kB; the configured error budget is 4.10 kB (`angular.json:53-56`).
- All 3 unit tests fail with `No provider for InjectionToken NGX_ECHARTS_CONFIG`.
- The only test file is the untouched Angular starter spec. Its final assertion still expects `.content span` and “a11y-charts app is running!”, neither of which exists (`app.component.spec.ts:21-25`).
- There are no component behavior tests, accessibility tests, end-to-end tests, lint script, coverage threshold, or CI workflow.

**User impact**

The team cannot distinguish a safe change from a regression, and a normal production build cannot be shipped.

**Fix**

First restore a green baseline: configure the ECharts provider in tests, replace starter assertions with component behavior contracts, add tests for keyboard navigation, IDs/IDREFs, reactive inputs, missing data, patterns, reduced motion, overflow, and multiple instances, and resolve the style budget intentionally. Add non-watch `test`, `lint`, production `build`, and axe/browser smoke commands to CI.

### FUNC-02 - The framework and chart stack are unsupported and vulnerable

**Severity:** High
**Scope:** Runtime and build dependency trees
**Target relationship:** Not standards-based

**Evidence**

- The project is on Angular 18.2; Angular lists version 18 among [unsupported versions](https://angular.dev/reference/versions).
- `npm audit --omit=dev` reports 9 production vulnerabilities: 8 high and 1 moderate.
- The affected direct runtime stack includes Angular core/common/compiler packages and ECharts 5.6.0. The ECharts issue is [GHSA-fgmj-fm8m-jvvx](https://github.com/advisories/GHSA-fgmj-fm8m-jvvx).
- The full tree reports 79 findings, including 3 critical build/development vulnerabilities.
- Current registry checks returned Angular 22.1.2, ngx-echarts 22.0.0, and ECharts 6.1.0. The repository has no Node version pin; local Node is 22.22.0, just below Angular 22's documented `^22.22.3` range.
- `@angular/animations`, `@angular/forms`, `@angular/platform-browser-dynamic`, and `@angular/router` are direct dependencies but have no source imports.

**User impact**

New work starts on an unsupported platform with known runtime XSS/DoS advisories and a vulnerable local toolchain. A forced audit fix would make unreviewed major-version jumps.

**Fix**

Create a dedicated upgrade branch. Pin a compatible Node version, remove unused direct packages, and migrate Angular one major at a time using official migrations. Align ngx-echarts with the selected Angular major and move to ECharts 6.1.0 or later. Re-run functional, visual, keyboard, and accessibility contracts after each major step; do not use `npm audit fix --force` as the migration plan.

### FUNC-03 - Changed inputs stay stuck on the first computed value

**Severity:** High
**Scope:** `data`; also a risk for plain-object `a11y` and `theme` changes
**Target relationship:** Not standards-based

**Evidence**

- `years`, `actualSeriesValues`, and `targetSeriesValues` are Angular `computed` values that read the plain `@Input() data` property (`a11y-line-chart.component.ts:270-274`). A plain input is not a tracked signal dependency.
- A direct component probe rendered data for 2020, then replaced `data` with 2030/2031 and called `ngOnChanges`. The results remained `[2020]` and `[1]` rather than the new values.
- `ngOnChanges` recalculates widths but does not invalidate the computed series.

**User impact**

A consumer that loads, filters, or refreshes chart data after initial render can show stale years and values while believing the input changed. This is a core reusable-component failure.

**Fix**

Use signal inputs (preferred on the upgraded Angular version) or copy changed inputs into private writable signals. Derive all options from tracked state. Add a host test that replaces data, theme, and accessibility configuration after first render and asserts the canvas options, table, accessible description, focus index, and width all update safely.

### FUNC-04 - Keyboard-selected data can move fully offscreen

**Severity:** Medium
**Scope:** Horizontally scrolling chart at 320-640 px
**Target relationship:** Not assigned to a WCAG criterion; it undermines the visible keyboard promise

**Evidence**

- At 320 px, the chart viewport was 272 px wide with 720 px scroll width.
- Focusing the first chart and pressing End correctly changed its label to “Current index 10 of 10.”
- The scroll container stayed at `scrollLeft = 0`.
- The 2025 tooltip landed from x=326 to x=550, completely outside the 320 px viewport.
- The polite live region correctly announced “Year 2017…” during a separate arrow-key check, so the defect is specifically visual synchronization, not the announcement logic.

**User impact**

A sighted keyboard user can move through data that is no longer visible and cannot tell which point is selected without manually coordinating horizontal scrolling.

**Fix**

When the selected index changes, scroll the point/tooltip into the chart viewport without causing document-level movement and respect reduced motion. Retest ArrowLeft/Right, Home/End, wrapping, and focus visibility at every overflowing width.

## Be-mark UX and implementation findings

### UX-01 - The repository is neither a finished library nor a production demo

**Severity:** Medium
**Scope:** Repository architecture and onboarding
**Target relationship:** Not standards-based

**Evidence**

- `package.json` is private and version `0.0.0`.
- The Angular project type is `application`; there is no library project, public API entry point, package exports, semantic-release/version plan, or consumer fixture.
- The README presents the component as reusable and tells consumers to copy a local component file.
- The current implementation is one 639-line TypeScript file plus a 292-line global stylesheet inside a two-instance proof-of-concept app.

**User impact**

Developers cannot make sound API, packaging, compatibility, or release decisions until the intended artifact is clear.

**Fix**

Choose one near-term product shape:

1. **Library-first:** create an Angular library project, public API, typed package exports, peer dependencies, a demo/consumer app, compatibility matrix, and semantic versioning.
2. **Prototype-first:** state that clearly, keep the demo app, and defer package promises while accessibility and API behavior stabilize.

Library-first is the stronger direction if multiple applications are expected to consume the chart.

### UX-02 - Global CSS and component concentration create integration risk

**Severity:** Medium
**Scope:** Shared chart component
**Target relationship:** Not standards-based

**Evidence**

- The component disables encapsulation with `ViewEncapsulation.None` (`a11y-line-chart.component.ts:99`).
- Its stylesheet publishes generic selectors such as `.controls`, `.sr-only`, `app-a11y-line-chart`, and `:root`, which can affect or be affected by a host application.
- All chart rendering, accessibility, styling resolution, patterns, tooltips, resizing, interaction, and formatting live in one class.
- Hiding the Actual series produced an ECharts console warning because the legend still declared a series that no longer existed.

**User impact**

Embedding the component can cause host-style collisions, and changes to one concern are likely to regress another.

**Fix**

Keep unavoidable dynamic-tooltip styles globally available but scope every rule under a unique component root. Move default custom properties to the host/root contract without globally redefining generic selectors. Extract pure formatting/evaluation, theme resolution, ID generation, chart-option construction, and interaction state into testable units. Keep the rendered API cohesive rather than splitting solely for file size.

### UX-03 - Demo semantics, docs, and governance have drifted

**Severity:** Low
**Scope:** Demo shell and repository documentation
**Target relationship:** axe best-practice findings, not graded WCAG blockers here

**Evidence**

- axe reported no `main` landmark, no H1, and content outside landmarks. Both chart titles are H2s.
- The README says the live region is assertive; the implementation uses `aria-live="polite"`.
- The README says multiple instances are fully self-contained, but their IDs are shared.
- The accessibility checklist is prose only; no matching automated contracts exist.
- “MIT (adjust as appropriate for your project)” is placeholder text, and there is no license file.
- There is no `.nvmrc`/`.node-version`, CONTRIBUTING guide, ownership guidance, or CI configuration.

**User impact**

The repository overstates verified behavior and gives returning contributors no dependable environment or definition of done.

**Fix**

Add a real page title/H1/main shell, synchronize docs with tested behavior, choose and add the actual license, pin Node, document setup/verification commands, and convert the accessibility checklist into executable tests plus a short manual screen-reader matrix.

## Outside-target advice

### MODERN-01 - Increase control size beyond the narrow AA spacing pass

**Severity:** Low
**Scope:** Display-option controls
**Target relationship:** AAA/enhanced usability advice, not a provisional AA blocker

**Evidence**

- Checkboxes render at 14.4 by 14.4 px and their labels at about 200 by 20.4 px.
- Selects render 19 px high.
- Vertical centers are approximately 26 px apart, so the controls narrowly satisfy the WCAG 2.2 AA spacing exception for 24 px targets.
- They do not approach the 44 by 44 px enhanced target, and the control-label font is only 11.52 px.

**Fix**

Use a comfortable 16 px text baseline and at least 44 px row height/active area for the demo controls. See [WCAG 2.2 SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) and the stronger 2.5.5 target.

## What is working well

- Both chart instances expose clear H2 titles, subtitles, native labelled checkboxes/selects, structured fieldsets, and well-formed data tables with captions and row/column headers.
- ArrowLeft/ArrowRight/Home/End interaction works, prevents unintended page scrolling, updates the current index, and produces a correct polite live-region message.
- Visual focus on the full chart is strong against the page background.
- Missing actual values remain gaps and are described consistently in the table/tooltips.
- Series visibility and pattern selections stay independent between rendered instances.
- The chart's intentional 720 px width is contained by its own horizontal scroller; the body overflow is traceable to the hidden table rather than the canvas.
- Source includes reduced-motion handling, resize cleanup, theme tokens, outcome semantics, and a meaningful text alternative instead of relying on ECharts ARIA alone.
- App and spec TypeScript compilation pass, the development app runs, and the working diff has no whitespace errors.
- The branch is aligned with `origin/main`, and the audit did not modify the three pre-existing source edits.

## Recommended remediation order

1. Create a stabilization branch without folding in unrelated work; decide whether to preserve or separately shelve the current uncommitted pattern experiment.
2. Decide library-first versus prototype-first and pin the supported Node baseline.
3. Upgrade Angular/ngx-echarts/ECharts in staged majors and remove unused dependencies.
4. Restore a green production build and replace the stale starter test with real component contracts.
5. Fix tracked input state before adding features.
6. Fix per-instance IDs/IDREFs, the keyboard control role, table-safe visual hiding, and target-series contrast.
7. Keep keyboard-selected points visible inside the chart scroller.
8. Scope styles and extract pure/testable component logic.
9. Add CI and update README/license/onboarding only after behavior is backed by tests.

## Retest and release gate

Do not call the baseline stable or WCAG-conformant until all of the following are true:

- `npm ci`, production build, lint, unit/component tests, and browser accessibility tests pass in CI.
- There are zero unresolved high/critical production dependency findings, and remaining development findings have a documented risk decision.
- Replacing `data`, `theme`, and `a11y` inputs after initial render updates all visual and accessible output.
- Every visible control has a valid name, role, state/value, and keyboard behavior.
- Multiple chart instances have zero duplicate IDs and every ARIA IDREF resolves within its intended component.
- Target and actual visual encodings meet required contrast in default, overlap, hover/focus, forced-color, and patterned states.
- There is no body-level overflow at 320, 375, 390, 480, 640, 768, 1024, 1280, or 1440 px; chart-only overflow remains operable and named.
- Arrow, Home, End, and wrap behavior keep the selected visible point/tooltip in view.
- VoiceOver + Safari and NVDA + Chrome smoke tests pass for chart discovery, instructions, point navigation, live updates, data-table navigation, series toggles, missing data, and multiple instances.
- Documentation, supported-version matrix, and package/demo positioning match the shipped artifact.
