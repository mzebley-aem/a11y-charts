# Project code and architecture audit — October 21, 2026

This is the pre-fix assessment. See [the fix follow-up](./AUDIT-FIXES-2026-10-21.md) for current disposition and verification.

## Assessment

The framework-free components have a sound foundation: strict TypeScript, separate semantic models, normalized data, scoped styles, safe default content rendering, useful accessibility state handling, and substantial tests. They are not yet consistent enough to treat as a hardened component family. Most actionable defects are in the line element's lifecycle and public boundary; much of the maintenance risk comes from implementing common infrastructure twice.

**Recommendation: create a private, source-level shared core and bundle its used code into each chart's distributable.** Consumers should not install or load a separate shared-functions package. Keep chart-specific semantic models, rendering, and interactions separate. Fix the confirmed behavioral defects before extracting their implementations.

This audit covers the current working tree, including the uncommitted bar package and shared-options changes. It is not an audit of just HEAD or the published preview. Existing implementation edits were preserved. This report is the only intentional source-tree addition from the audit.

## Prioritized findings

### 1. P1 — A line chart mounted while hidden never initializes when revealed

**Source:** `packages/line-chart/src/a11y-line-chart-element.ts:1359–1432`.

`#mountChart` exits when the container has zero width or height. The ResizeObserver is created only after that early return. A chart first mounted in a hidden tab, collapsed panel, or delayed stylesheet/layout has no observer to retry initialization.

**Browser reproduction:** append a populated chart beneath `display:none`, allow rendering, then reveal the parent. Its chart container became 1,248 px wide but still contained zero canvases.

**Fix:** observe the container before checking size; initialize once it has usable dimensions, then resize the existing adapter. Cover hidden-to-visible transitions and connect/disconnect before visibility in real-browser tests.

### 2. P1 — Live line-chart updates discard primary keyboard focus

**Source:** `packages/line-chart/src/a11y-line-chart-element.ts:454–470, 596–607, 618–631`.

Every queued render destroys and rebuilds the owned content. Focus recovery uses `data-focus-key`, but the primary range navigator does not have a key. The stepper and display controls also need a complete focus-preservation policy.

**Browser reproduction:** focus the line navigator, replace data, allow the update; `document.activeElement` becomes `BODY`.

**Fix:** preserve the navigator/control nodes or restore focus through stable identities, with sensible fallback when a selected item disappears. Track period identity, not merely array index, if updates can reorder or prepend periods. The bar details implementation already uses stable category IDs for focus keys.

### 3. P2 — Point-change event details expose mutable internal state

**Source:** `packages/line-chart/src/a11y-line-chart-element.ts:1269–1284`.

`x: datum.x` passes the internal Date object directly. `targetDifference` and `baselineDifference` similarly expose model objects rather than copies. This differs from the defensive copies used by the data getter and data-change event.

**Browser reproduction:** a point-change listener calls `event.detail.x.setFullYear(1999)`; the next `chart.data` getter reports 1999 instead of the original 2025. No setter or deliberate source update was involved.

**Fix:** copy Dates and nested difference objects at every public callback/event boundary. Test mutation of each nested payload, not only top-level arrays and target ranges.

### 4. P2 — Reconnecting an open line data dialog can leave it open but nonmodal

**Source:** `packages/line-chart/src/a11y-line-chart-element.ts:274–278, 688–778`.

Disconnect disposes the chart but does not explicitly close/reset the dialog. Render decides whether to call `showModal()` using the dialog's `open` property. That property is insufficient to establish membership in the browser's modal top layer after removal/reinsertion.

**Browser reproduction:** open Data, remove the chart, reappend it. The dialog reports `open === true` but `matches(':modal') === false`. The UI no longer has native modal behavior.

**Fix:** centralize close/disconnect/reconnect behavior and restore through `showModal()`, with a documented reopen policy and synchronized public state. Bar already explicitly closes on disconnect and records a reopen preference; share a tested controller after reconciling edge cases.

### 5. P2 — Line configuration accepts values that crash rendering or invalidate defaults

**Source:** `packages/line-chart/src/config.ts:136–177`; line element config setter and heading-level resolution.

Precision is rounded and lower-bounded but never upper-bounded. Other options are copied via object spread without consistent runtime validation. Invalid `tableVisibility` and heading levels survive resolution, and explicitly undefined booleans overwrite defaults. The config setter also dereferences `value` without a null guard.

**Browser reproduction:** `chart.config = { decimalPlaces: 1000 }` produces an uncaught `minimumFractionDigits value is out of range` error and leaves only the title. Direct resolver checks also preserve heading level 9 and an invalid table mode. JavaScript/CMS integrations are not protected by TypeScript declarations.

Bar already validates precision in 0–20, booleans, enums, heading level, and nullish config. Extract equivalent common validators and retain chart-specific defaults. Include axis precision, dimension bounds, patterns, and theme numeric values in the input audit.

### 6. P2 — Dependency maintenance differs between packages and the root remains risky to run

Live `npm audit` results:

|---|---:|---:|---:|---:|
| Root Angular reference | 5 | 59 | 22 | 7 |
| Line, including development dependencies | 0 | 2 | 0 | 0 |

Line findings are `source-map-js` and Vite, with non-major fixes reported available. The installed demo builders already differ: line Vite 8.2.1 and bar Vite 8.3.4. The line production-only audit reported zero findings. Registry counts include transitive/meta-vulnerability records and do not mean every advisory is exploitable in this application's usage.

**Fix:** refresh the line lockfile deliberately and rerun verification; do not apply an indiscriminate forced upgrade. Isolate/archive the frozen Angular reference or upgrade it if it remains runnable. The root `start`, `build`, and `test` scripts still select that reference, which obscures the active project and its security posture. Vercel currently installs/builds the line package, not the root Angular tree.

### 7. P2 — Public pure helpers cannot be imported independently in Node/SSR

**Source:** both `src/index.ts` files, both `package.json` export maps, and the element classes extending HTMLElement.

Each public index eagerly exports the custom element along with the semantic/CSV helpers. Importing either built public entry in Node throws `HTMLElement is not defined`, even if the consumer only wants `buildBarModel` or `buildSemanticModel`.

Bar CSV additionally requires DOMParser/document when context or a data note is supplied. Line has a server fallback that strips tags with a regex; it is not equivalent to browser parsing and can retain script text or encoded entities differently. Calling all of these helpers “pure” conceals environment dependencies.

**Fix:** export a DOM-free `./core` entry; keep registration and elements in browser entries. Define a consistent rich-text-to-plain-text contract for CSV: require already-normalized text in the pure layer or use an environment-independent parser. Bundle declaration files so published types do not reference a private workspace package.

### 8. P3 — Line English plural fallback ignores its own singular translations

**Source:** `packages/line-chart/src/messages.ts:77–93`.

The fallback always selects the English `.other` template, ignoring the available English category-specific template. Confirmed output: `Chart data updated. 1 periods are available.` This also affects comparable-period and percentage-point wording.

**Fix:** choose override category, override `.other`, English category, then English `.other`. Share the message engine, not the chart-specific catalogs. Bar's implementation already consults the English category.

### 9. P2 — Shared event names conceal different event semantics

**Source:** line data/config setters and `#dispatchDataChange`; bar render signatures at `a11y-bar-chart-element.ts:474–503`.

Line emits data-change after assigning data even if equivalent, but baseline-only changes alter its semantic model without that event. Bar compares serialized source state. Bar display-change covers property-driven presentation changes; line display-change is emitted for its own controls/legend, while property-driven theme, messages, filtered, and config updates do not follow that contract. Ready payloads also differ.

These differences complicate a consuming application switching chart types or keeping external summaries/exports synchronized. They are observable contract differences, not a reason to force identical domain payloads.

**Fix:** document whether events describe assignments, actual source changes, or user actions. Standardize common timing, initial-render behavior, source tagging, and state transitions; retain typed chart-specific payload fields. Prefer revision/dirty tracking over repeated serialization.

### 10. P3 — Bar unnecessarily retains the complete original input graph

**Source:** `packages/bar-chart/src/a11y-bar-chart-element.ts:84, 134–136`.

`#dataInput` is assigned on every data setter and never read. The validated copy is already retained separately. Extra properties or references on caller records therefore remain reachable for the lifetime of the chart/current assignment, despite being discarded by validation.

**Fix:** delete this field and assignment. This is confirmed unnecessary retention, not evidence of an unbounded leak across successive updates. Line also retains invalid input for retranslation; storing structured error codes/parameters, as bar does, would avoid keeping arbitrary invalid graphs alive.

## Efficiency and memory lifecycle

- **Full rendering is the main optimization target.** Line calls `#disposeChart()` on every queued render, replaces the root content, and creates a new ECharts instance. A title, context, theme, or disclosure change can trigger the same expensive path as new data. Bar also reconstructs its rows, details controller, tables, and listeners. Use semantic/display dirty flags and persistent DOM/controller instances. Optimize lifecycle before small loop changes.
- **Formatting repeats work.** Line repeatedly resolves config and creates Intl formatters, including during width calculation, tables, labels, and axis formatting. Bar constructs number formatters per value and rebuilds its entire message dictionary on each `message()` call. Resolve config/catalog once per render and reuse a small formatter set. Prefer per-instance/render caches or bounded caches; do not introduce an unbounded global cache.
- **Use model text consistently.** Line table period/actual cells re-run callbacks instead of using the model's formatted strings; CSV already prefers model text. Stateful or expensive callbacks can produce inconsistent representations. Calculate canonical formatted values once per source/format revision.
- **Avoid work for unused views.** Both materialize complete table content for background access and a dialog/inline view. Preserve the accessible data contract, but lazily create or refresh secondary presentation when needed. Do not remove the background description without replacing its accessibility relationship.
- **Large data needs an explicit budget.** Line zoom bounds and bar leader selection use spread into `Math.min`/`Math.max`; sufficiently large arrays can exceed argument limits. Replace these with reductions. Both components render every datum and do not declare a tested maximum. Do not solve this by silently sampling away accessible data.
- **Measurements are preliminary.** A local Node smoke benchmark averaged about 10 ms for a 100-row bar model and 43 ms for 1,000 rows over three runs. These are not browser render budgets or statistically controlled benchmarks. Establish representative dataset and multi-chart measurements before setting targets.
- **Good cleanup exists.** Line disconnects ResizeObserver, removes its window listener, unsubscribes its legend listener, disposes ECharts, and clears its live timer. Bar aborts details listeners and clears the details timer on destroy. Detached-node listener cycles alone are not leaks.
- **Finish cancellation handling.** Line does not retain animation-frame handles; its scroll-settling loop relies on index/connection checks. Render/disconnect generation tokens and explicit cancellation would prevent stale work. Microtask render flags reset on disconnect can also permit duplicate queued work during rapid reconnects. Test these transitions instead of assuming normal disconnection proves correctness.

## DRYness, organization, and readability

There are roughly 5,716 lines across the two package source directories. The element classes alone are 1,445 lines (line) and 932 (bar). Their responsibilities include state normalization, rendering, focus, dialogs, disclosure, formatting, export, events, and renderer lifecycle. That concentration makes bug fixes difficult to transfer between packages.

The strongest extraction candidates are:

| Shared responsibility | Current duplication/drift | Suggested home |
|---|---|---|
| Rich-content allowlist and URL policy | Nearly equivalent sanitizer duplicated; server fallback differs | `chart-core/content` |
| Locale, precision, booleans, heading and enum validation | Bar stronger than line | `chart-core/config` |
| Template/plural interpolation | Different fallback/validation engines | `chart-core/messages` |
| CSV escaping and download handling | Line quotes all cells/preserves numeric negatives; bar conditionally quotes and protects all leading negatives; URL cleanup timing differs | `chart-core/csv` and browser download helper |
| Scalar/range copying and comparison | Repeated target primitives and outcome logic | `chart-core/targets` |
| Dialog state, focus recovery, disclosure events | Independent complex implementations | `chart-core/dom` controllers |
| Scheduling and disposal | Microtask/render cleanup patterns repeated | Small lifecycle helper after defining required behavior |
| Base action/table/dialog styling | Parallel namespaced rules | Build-time shared CSS source, retaining per-chart namespaces |
| Demo/package scripts and tool versions | Similar scripts/configs and drifting locks | Root workspace tooling |

Prefer composition with narrow functions/controllers over a large `BaseChartElement` superclass. Do not make ECharts a dependency of the shared core or the bar bundle. Keep bar details and line period navigation specific until there is a real shared contract.

Comments generally explain accessibility intent well, especially modal focus and details-card behavior. The bigger readability problems are multiple statements on a single line, nested conditional expressions, huge method/class scope, and string unions recovered with casts. Expand consequential branches, name intermediate decisions, and use typed message-key mappings. More comments will not compensate for unclear structure.

Useful cleanup: remove the unused bar `#dataInput`, the unused return-value call to `safeLocale` in bar `formatMessage`, the unused `live` local in line render, and the duplicate `#focusKey(activeKey)` invocation in bar render. The `autoDetectGaps` line-chart branch currently maps only values after the last non-null value back to null, so it appears behaviorally redundant; clarify its intended contract or retire it. Add no-unused checks/linting after addressing actual dead code, with a consistent formatter for source files.

The root README links `AUDIT.md`, but the existing older report is `AUDIT-2026-08-18.md`. Spec test totals also lag the current 184 tests. Generated demo HTML is large, so reviews should focus on source/templates and verify reproducibility separately.

## Hardening

The default paths use textContent and a small HTML allowlist. Dangerous rich-content elements and attributes are dropped, URL schemes are restricted, target values are normalized before protected rendering, and CSV formula prefixes receive protection. These are meaningful strengths.

The legacy `buildTooltipHtml` callback returns HTML directly to ECharts. Treat it as trusted application code and document that untrusted content must never be concatenated into it; its mere existence is not evidence that default charts have XSS. Prefer the DOM renderer hook and consider removing the legacy hook if compatibility is unnecessary. Sanitizer/CSV tests should cover encoded/control-character URLs, malformed markup, nested content, spreadsheet injection payloads, and localized values in both packages through one shared implementation.

Bar message-key filtering uses `key in ENGLISH_MESSAGES`, unlike line's own-property check. Replace inherited-key acceptance with `Object.hasOwn`/equivalent and make blank/invalid values fall back consistently in exported helpers as well as element setters. Do not describe this alone as demonstrated exploitable prototype pollution.

Bar's `showModal()` catch falls back to an `open` attribute, which does not provide native modality/background inertness. Define browser support and offer a real inline fallback or explicit error for unsupported dialog APIs. Avoid silently presenting a nonmodal view as a modal one.

## Self-contained distribution design

Today, `npm run build` uses tsc plus CSS copying. It emits multiple JS modules; line's adapter retains bare ECharts imports. The demo builds already show that independent IIFE bundling works, but those bundles include demo content and are not production library entry points.

Recommended source layout:

```text
packages/
  chart-core/       # private source package, common pure helpers + isolated DOM helpers
  line-chart/       # line model, element, ECharts adapter, scoped styles
  bar-chart/        # bar model, element, details controller, scoped styles
tooling/            # shared build/test configuration
```

Recommended outputs per chart:

1. An ESM entry for application bundlers, with private core code bundled into the chart artifact.
2. A standalone browser entry that registers the custom element; line includes its required ECharts modules. Bar includes no ECharts.
3. Scoped CSS alongside the script, with an explicitly designed embedded-style variant only if one-file installation is required.
4. A DOM-free helper entry and self-contained declarations, with no unresolved private-core imports.

Build the charts independently so a bundler does not extract a mandatory common runtime chunk. Small shared functions will appear in both standalone files when both are used; that is a reasonable tradeoff for easy installation. Source DRYness and runtime byte deduplication are different goals. Consider an optional combined distribution only if measured demand justifies it.

The fresh demo builds measured 662.19 kB / 218.26 kB gzip for line JS and 78.31 kB / 22.05 kB gzip for bar JS. These include fixtures/localization/demo UI and are **not component-only bundle measurements**. Establish component-only budgets after creating dedicated library entries; moving source to a shared core does not by itself shrink ECharts.

Add artifact-level smoke tests that load each packed distribution in an empty page, without workspace sources or a shared script. Verify both charts together, duplicate registration, CSS scoping, declarations, no private imports, and offline standalone loading. Test actual packed exports, not just Vite's source graph. No current repository CI workflow was found; root scripts still target Angular.

## Suggested implementation sequence

1. Fix the confirmed lifecycle, focus, mutable-event, and invalid-config defects with targeted browser regressions. Refresh the line development dependencies.
2. Establish a common feature/event contract and a parameterized parity suite. Keep deliberate domain differences explicit.
3. Extract pure utilities first: config primitives, messages, targets, CSV encoding, rich-content handling. Preserve public APIs through chart-specific facades where useful.
4. Extract dialog/disclosure/focus controllers once the corrected lifecycle behavior is tested. Keep renderer and navigation implementations separate.
5. Replace unnecessary full reconstruction with persistent DOM/renderer updates; cache resolved formatting per revision. Measure representative workloads and repeated mount/update/remove cycles, including heap snapshots.
6. Add independent library bundles, DOM-free helper exports, declaration bundling, workspace verification scripts, and packed-artifact CI smoke tests. Update docs to distinguish the Angular reference, demos, local package builds, and published artifacts.

Do not begin by moving both giant element classes into a universal chart framework. A small private core plus chart-owned rendering gives the requested end-user simplicity without coupling the two chart types unnecessarily.
